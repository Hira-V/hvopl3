# hvopl3 drv: a MIDI driver for hvopl3 chips

`drv/` plays MIDI 1.0 on 1 to 32 hvopl3 chips. It allocates voices, maps instruments from banks, and
turns controllers into register writes and hvopl3's mixer extensions (pan, sends, gain). It does the
job the DOS sound drivers did for the AdLib and Sound Blaster cards, written new for hvopl3. It does
not imitate any existing driver.

It is optional. The chip library does not depend on it: a program that wants only the chip compiles
only `src/hvopl3.cpp`. Nothing in `drv/` depends on anything outside this repository.

This document covers the API and every policy the driver chose. Section 11 has its measured speed.

## 1. Building

| File | |
|---|---|
| `drv/hvopl3_drv.hpp` | The API: `Driver`, `Pool`, `Patch`, `Config`, the calls, and a C ABI (`hvopl3_drv_*`) |
| `drv/hvopl3_drv.cpp` | The driver: one translation unit |
| `drv/hvopl3_drv_tables.inc` | The hirav curve, the pitch exponent and the vibrato sine. Generated by `tools/gen_drv_tables.py` and checked in |
| `drv/banks/` | DMXOPL3's General MIDI bank (`DMXOPL3-GS.wopl`, MIT: `LICENSE-DMXOPL.txt`), for the tests and for programs that want it. The driver never embeds it |

```sh
c++ -std=c++17 -O2 -ffp-contract=off -Isrc -Idrv -c drv/hvopl3_drv.cpp
```

The driver builds with the chip's flags on every target, including `-ffp-contract=off`, although it
uses no floating point. It follows the chip's rules too: C++17, no allocation, no exceptions or RTTI,
no writable globals, and nothing from the C library but `memset` and `memcpy`. The bare-metal builds
(RV32 and RV64, scalar and vector) link with `-nostdlib`, so neither a C library nor libgcc is needed.

**The most chips** is a build option: `-DHVOPL3_DRV_MAX_CHIPS=N`, 1..32, default 32. Every array sized by
it follows it (slot indices reach 576, in 16 bits), and `init`/`configure` clamp `Config::chips` to it.

| `HVOPL3_DRV_MAX_CHIPS` | `sizeof(Driver)`, A25 | 64-bit host |
|---|---|---|
| 4 | 7,836 | 8,728 |
| 16 | 21,012 | 24,496 |
| 32 (default) | 38,580 | 45,520 |

All state lives in three caller-owned things: the `Driver` (above), the bank `Pool` (4.3 KB a bank),
and the `Chip`s. On the A25 the code is about 22 KB and the
tables about 8 KB. One message touches its channel's voices and a few list heads, and the control
period touches only the channels that changed. The working set of one event is a few hundred bytes.

## 2. API

Namespace `hvopl3::drv`, header `drv/hvopl3_drv.hpp`.

```cpp
#include "hvopl3_drv.hpp"

static hvopl3::Chip chips[4];
static hvopl3::drv::Driver drv;
alignas(16) static uint8_t pool_mem[80000];          // drv::pool_bytes(16): room for DMXOPL3's 14 banks
static int32_t dry[2 * 480], rev[2 * 480], cho[2 * 480];

void setup(const void *wopl, size_t size) {
    using namespace hvopl3;
    drv::Pool *pool = drv::pool_init(pool_mem, sizeof pool_mem);
    drv::load_wopl(*pool, wopl, size);                // e.g. drv/banks/DMXOPL3-GS.wopl
    drv::Config cfg = drv::default_config();
    cfg.chips = 4;
    drv::init(drv, *pool, chips, cfg);                // the chips are set up at the first render
}
void block(const uint8_t *msg, uint32_t len, uint32_t frame) {
    hvopl3::drv::send(drv, frame, msg, len);          // any number of messages, each at a frame of the block
    memset(rev, 0, sizeof rev); memset(cho, 0, sizeof cho);
    const hvopl3::Output out = {dry, rev, cho, false};
    hvopl3::drv::render(drv, out, 480);               // 10 ms at 48 kHz
}
```

### Banks

| Call | |
|---|---|
| `pool_bytes(banks)` | Memory for a pool of that many banks |
| `pool_init(mem, bytes)` | A pool in `mem` (8-aligned). The header, the banks and a hash index all live inside it |
| `pool_clear(pool)` | Empty it. A driver that uses the pool must then be `configure`d |
| `set_patch(pool, percussion, msb, lsb, program, patch)` | A patch. Its bank is made if needed. False when the pool is full |
| `find_bank`, `find_patch` | Lookup by (kind, MSB, LSB): a hash, O(1) |
| `load_wopl(pool, data, size)` | A WOPL file, versions 1 to 3, all of it or nothing (section 9) |
| `set_levels(pool, programs, kits, nkits)` | Level corrections into the patches' gain fields (section 8) |

A `Patch` holds the four operators' registers 20, 40, 60, 80 and E0 in the chip's order (each
channel's modulator first), the two C0 feedback/connection nibbles, the kind (blank, 2-op, 4-op,
pseudo-4-op), a note offset for each voice, the velocity offset, the second voice's detune, the
percussion key, the gain correction, the WOPL rhythm-mode drum type (kept, not used) and a fixed-note
flag.

### The driver

| Call | |
|---|---|
| `default_config()` | 1 chip, 48 kHz, the bank's curve (hirav by default), soft pan, corrections, re-strike and the returning note on, deep tremolo and vibrato from the bank |
| `init(drv, pool, chips, config)` | Set up. The chips are initialised at the first render |
| `configure(drv, chips, config)` | A new chip count, rate or setting: a full reset at the next render. The banks are kept |
| `update(drv, chips, config)` | New settings without a reset where none is needed: the notes sound on and every channel keeps its state. The curve, `level_corrections` and `gain_remainder` re-level every sounding voice at the next render; `restrike` and `pressure_vibrato` apply at once; the deep tremolo and vibrato (register BD) and, in direct mode, the chips' `HQ_*` and `NO_CLIP` flags (`hvopl3::set_flags`) at the next render's start. Any other change is `configure`'s |
| `send(drv, frame, msg, len)` | A complete MIDI message, or a SysEx `F0 ... F7`, at a frame of the next block. False if the queue (256) is full: render, then send again. Malformed and unknown messages are consumed |
| `send3(drv, frame, status, a, b)` | The same, from bytes |
| `render(drv, out, frames)` | Direct mode: the block, every chip summed into `out`. Returns `SOUNDED` if any chip made sound |

`NO_CLIP`...), `curve`, `stream`, `hard_pan`, `level_corrections`, `restrike`, `gain_remainder`,
`pressure_vibrato`, `deep_tremolo` and `deep_vibrato` (-1 the bank's flag, 0 off, 1 on), `returning`.

The C ABI has the same calls on caller-allocated memory: `hvopl3_drv_size()`,

`hvopl3_drv_pool_init()`, `hvopl3_drv_load_wopl()`, `hvopl3_drv_set_levels()`, `hvopl3_drv_init()`,

`hvopl3_drv_render_stream()`, `hvopl3_drv_reset()`, `hvopl3_drv_panic()`. `KitLevels` is laid out as
`{uint8_t kit; int8_t levels[128];}`, so a C table of that shape can be passed as it is.

## 3. Time and the control period

Messages carry a frame within the block about to be rendered. Frames arrive in order: one earlier
than the message before it is taken as that message's frame. One at or past the block's end is
clamped to the last frame. The driver renders each chip only as far as it must before a write, so
every message is applied at its own sample.

The **control period** is 64 frames at 48 kHz and 128 at 96 kHz (1.33 ms), counted from `init`.
Vibrato, portamento, pitch bend, the start of stolen voices and the freeing of silent ones all happen
at period boundaries. Periods fall on absolute frames, so the same messages at the same frames give the
same samples whatever the block sizes. The tests check blocks of 1, 7, 64, 480 and 4000 frames.

At one frame the order is: a pending `init`, `panic` or `reset` (only at a block's start), then the
control period if one falls there, then the messages in the order sent.

**Output.** In direct mode the dry block is cleared (unless `add_dry`), and then every chip adds into
it as it renders. Each chip's own output is clipped to 16 bits before the sum (unless `NO_CLIP`), as
`add_dry` after a first chip would do. A chip renders in pieces between writes, so no chip can be the
one that writes first. The buses are added to, as `hvopl3::render` does.

## 4. MIDI

| Message | What the driver does |
|---|---|
| Note On / Off | Velocity 0 is Note Off. Note Off's velocity is ignored. A Note Off releases the oldest sounding voice of that note on the channel. A Note Off for a note whose stolen voice has not started yet cancels it |
| Program Change | For notes after it. Latches CC 0/32. On a percussion channel it selects the kit |
| Pitch Bend | 14-bit, times the RPN 0 range (default 2 semitones), on every voice of the channel, released ones too, at the next control period |
| Channel Pressure | Adds to the vibrato depth (CC 1 + pressure, at most 127) with `pressure_vibrato`. Off by default, as in General MIDI 2's default |
| Poly Pressure | Consumed, no effect |
| CC 1 | The driver's vibrato depth (section 7) |
| CC 5, 65, 84 | Portamento time, on/off, control (section 7) |
| CC 6 / 38, 96 / 97 | Data entry MSB / LSB, increment / decrement, for the selected RPN |
| CC 98-101 | NRPN and RPN select. RPN 7F/7F is null. Of the NRPNs, GS's per-drum ones take effect (section 5); the others make data entry do nothing |
| RPN 0 | Bend range: MSB semitones, LSB cents (0-99). Increment and decrement step one cent, carrying into semitones |
| RPN 1 | Fine tuning: 14-bit, 8192 is centre, ±100 cents. Increment and decrement step one unit |
| RPN 2 | Coarse tuning: MSB - 64 semitones. Increment and decrement step one semitone |
| CC 7, 11 | Volume and expression: every voice of the channel at once |
| CC 10 | Pan (section 8) |
| CC 64 | Sustain (≥ 64 on). A Note Off under it holds the note. Pedal up releases what nothing else holds |
| CC 66 | Sostenuto: holds the notes whose keys are down when it is pressed, nothing played after, and not notes held only by the sustain pedal |
| CC 67 | Soft pedal: kept, no effect |
| CC 91, 93 | Reverb and chorus send (defaults 40 and 0), through `set_sends` on every voice of the channel |
| CC 120 | All Sound Off: every voice of the channel cut (release rate 15), pedals or not |
| CC 121 | Reset All Controllers, as GM2's recommended practice: modulation 0, expression 127, pedals off, portamento off, pressure 0, bend centre, RPN/NRPN null. Program, bank, volume, pan, sends, the RPN values and the percussion flag are kept |
| CC 123-127 | All Notes Off: every key on the channel up. The sustain and sostenuto pedals still hold |
| SysEx | GM System On, GM System Off, GM2 On, GS reset (checksum checked), XG System On: each a full reset (every note released, every controller its default, master volume and tuning reset, percussion back to the default). Master Volume (universal real-time, its MSB 0-127). Master Fine Tuning (14-bit, ±100 cents) and Master Coarse Tuning (MSB - 64 semitones). GS "use for rhythm part" (section 5). Others are consumed |

Running status is not taken: each message comes whole.

**Re-strike** (`restrike`, on by default): a Note On for a note already sounding (key down or held by a
pedal) on the channel keys that voice off at once and on again at the next control period, so the
chip sees an edge. The new velocity and the current program apply. If the program's patch is of
another kind, the old voice is released and the note gets a new voice. With `restrike` off, notes
stack.

**The returning note** (`returning`, on by default): a Note On whose note still has a voice on the channel
that is releasing -- same channel, same note, same patch, not cut -- keys that voice again, with no cut
and no wait. The chip restarts the attack from the envelope's level at that moment, as a real OPL3 does
when a channel is keyed again, so a slow attack repeated quickly builds up instead of starting from
silence each time (fast staccato chords on a string patch). The rule by kind:

- 2-op: a released 2-op voice that played the patch's first half.
- 4-op: a released 4-op voice whose pair is still in 4-op mode; the pair is keyed again whole.
- Pseudo-4-op: both halves, each still releasing on its own channel. If one half has been taken by
  another note meanwhile, the voice is not returned and the note gets a new one (both halves).

Of several such voices the newest is taken. A voice cut by All Sound Off, a steal or the release cap is
never returned to: it is falling at release rate 15 and starts over. A held note (key down or kept by a
pedal) is re-struck instead (above). With `returning` off a new voice is allocated, as for any note.

**Missing patches.** If the selected bank has no patch for a program, or it is blank, the same program
in bank 0 (MSB 0, LSB 0) of the same kind plays. On a percussion channel this means the same key in
kit 0. If that is blank too, the note is silent and takes no voice.

## 5. Percussion channels and kits

Percussion is a flag on each channel. A percussion channel takes its patches from the percussion banks:
each note selects a patch, which plays at the patch's percussion key plus its note offset. Everything
else is as on a melodic channel: voices, levels, pan, sends, every controller, bend and vibrato
included.

The flag is set or cleared by:

- **The default:** channel 10 (index 9) only. It is only a default; every route below can clear it.
- **GM2:** bank select MSB 120 makes the channel rhythm, 121 makes it melodic. Like any bank select,
  it takes effect at the next Program Change.
- **GS:** the "use for rhythm part" SysEx (`F0 41 dev 42 12 40 1x 15 vv sum F7`), on any part, at once.
  Off makes the part melodic. Map 1 and map 2 both make it rhythm. A WOPL bank has one set of kits, so
  map 2 selects nothing different from map 1. The part block x is mapped as GS numbers its parts: block
  0 is part 10, blocks 1-9 are parts 1-9, blocks A-F are parts 11-16.
- **XG:** bank select MSB 127 (drum kit) and 126 (SFX kit) make the channel rhythm at the next Program
  Change. A Program Change with any other MSB makes a rhythm channel melodic, but only in XG mode. XG
  mode starts with an XG System On, which also makes channel 10 behave as if MSB 127 were selected.
  The rule also applies on a channel that selected MSB 126 or 127 itself. Outside XG mode, other MSBs
  leave the flag alone, so a General MIDI file that sends MSB 0 on channel 10 keeps its drums. GM,
  GM2 and GS resets end XG mode.
- **The host:** `set_percussion(channel, 1 or 0)`, for players of formats that put drums elsewhere.
  While the host's setting stands, it wins over every MIDI route and survives resets. `-1` hands the
  channel back to MIDI, and the next reset restores the default.

A channel never becomes percussion by inference, only through one of these routes. GM, GM2, GS and
XG resets restore the default (channel 10 only, plus any host settings). Reset All Controllers does
not change the flag.

**Kits.** The kit is the channel's program number. It is the WOPL percussion bank with MSB 0 and LSB =
program: DMXOPL3's kits 0 (Standard), 16 (Power) and 25 (TR-808). This holds for every standard:

| Standard | How the channel is chosen | Kit |
|---|---|---|
| GM | channel 10 | program (GM files leave it 0: kit 0) |
| GM2 | bank MSB 120 | program; the bank LSB is not used |
| GS | the rhythm-part SysEx, or channel 10 | program, as GS selects kits; bank select is not used on a rhythm part |
| XG | bank MSB 127 or 126 | program; an SFX kit (126) has no bank of its own, so it falls back to kit 0 |

A kit that does not exist, or a key that is blank in it, falls back to kit 0's key.

**GS's per-drum settings.** On a percussion channel, the NRPNs GS defines for a drum instrument, its key
the NRPN LSB (CC 98) and the value data entry's MSB (CC 6): 18h pitch (semitones from 64), 1Ah level,
1Ch pan, 1Dh reverb send, 1Eh chorus send. The level is a share of the channel's expression (so every
curve takes it), the sends shares of the channel's sends (a key no NRPN names keeps the channel's: 127
of 127), the pan about the channel's (the drum's pan plus the channel's less 64; 0, GS's random, and the
default, leave the channel's pan: nothing here is random). Level, pan and sends reach the key's voices
at once, sounding ones too; pitch the key's next note. The settings belong to the channel's drum map, as
in GS: map 1 for every percussion channel but a part the rhythm-part SysEx puts on map 2. They are kept
by Reset All Controllers, which nulls the NRPN selected, and return to the defaults at every reset (GM,
GM2, GS, XG). On a melodic channel they, and every other NRPN, are consumed. Data entry LSB, increment
and decrement do nothing for an NRPN.

## 6. Voices: kinds, 4-op pairs, allocation and stealing

A **slot** is one chip channel: 18 a chip, 18 × chips in all.

- **2-op**: one channel.
- **4-op**: a channel pair (0+3, 1+4, 2+5 in each register array) with its 0x104 bit set. Operators 1-4
  are the pair's first channel's modulator and carrier, then the second's. The pair's first channel
  carries the extensions (pan, sends, gain), as the chip has it.
- **Pseudo-4-op**: two 2-op voices, which may be on different chips. The second plays the patch's
  operators 3 and 4 with its own C0, note offset and detune. If only one channel can be found, the
  first voice plays alone.
- **Blank**: no sound, no voice.

**4-op pairs: dynamic.** Each chip starts with every pair in 2-op mode. A pair changes mode only while
both its channels are silent, so a sounding voice is never disturbed. A 4-op voice takes, in order:
a free pair already in 4-op mode, then a free 2-op pair (switched), then a released 4-op voice, then a
2-op pair whose channels are free or released (cut and switched), then a held 4-op voice (stolen),
then a held 2-op voice's pair (its voices stolen, the pair switched). A 2-op voice prefers a channel in
no pair (6-8 and 15-17 in each array), then a channel whose pair is already broken, then any 2-op
channel. On a chip with no other free channel, it switches a free 4-op pair back to 2-op. Whole free pairs are
thereby kept for 4-op voices, and pairs stay 4-op while 4-op voices use them.

**Allocation order:**

1. **Free and silent.** Among the chips with a usable free channel, the one with the fewest busy
   channels (ties: the lowest chip). This spreads voices evenly over the chips.
2. **Released, quietest.** Among the 32 oldest released voices: the highest of (its level in 0.75 dB
   steps, see below) + (what its release has taken since). The release estimate is
   `(control periods since release × 71) >> (15 - RR)`, from the slowest carrier's release rate. It
   models rate 15 falling 96 dB in about 2.4 ms and each lower rate taking twice as long. A voice whose
   pair would have to change mode scores 64 lower.
3. **Held, missed least.** Among the 32 oldest held voices (key down or kept by a pedal), never one
   started in the current control period: the highest of level + 24 if only a pedal holds it + its age
   (control periods / 64, at most 16). A voice whose pair would have to change mode scores 32 lower.
4. Nothing: the note is not played.

A voice's **level** is the attenuation of its loudest carrier: the patch's own total level plus the
curve's attenuation for its velocity, volume, expression and master volume. Ties go to the older
voice, then the lower slot. Nothing is random: the same input always picks the same voices.

**Quiet steal.** A stolen or reused voice that still sounds is cut: release rate 15 on all its
operators, then key off. The new note starts at a following control period, once the chip reports
the channel silent. It waits at most 3 periods (4 ms), or 16 periods when the pair's mode must change.
A free voice starts at once, at its message's frame. Stolen notes can therefore start up to a few
milliseconds late. That is the price of avoiding the click of re-keying a sounding channel.

**Silence detection.** A released voice is freed at the first control period after it can make no
more sound. The chip says so (`hvopl3::inaudible`, src's query): every operator the voice is heard
through (its connection's carriers) is keyed off, in its release, and attenuated by at least 72 dB --
envelope, total level and key scaling together, which includes the curve's attenuation the driver put
into the total level. That is the renderer's own silence (`QUIET`): there a full-scale operator's output
is below one unit of the chip's output (16-bit scale), and `render()` skips the voice whole. The
envelope only falls further in its release and the tremolo only adds attenuation, so from then on the
voice's output is exactly zero, in every quality mode and at any gain (`t_ext` checks it, FM and
additive, 2-op and 4-op, with tremolo and +24 dB of gain). Nothing that is heard is cut: the threshold
is not a guess at audibility but the point where the chip produces nothing at all. Freeing there instead
of at the envelope's end (96 dB, the chip's `active`) frees a release-rate-4 voice about a quarter
sooner, and voices that start quiet (soft notes, low volume, quiet patches) much sooner. As it is freed
the voice is also cut (release rate 15): it is silent already, and a release that never ends (rate 0)
would otherwise keep the chip working on it. A voice whose envelope ends anyway is freed as before.
An idle chip therefore costs nothing.

**Release cap.** Some patches never finish their release: DMXOPL3 has carriers with release rate 0.
A voice still sounding 10 s after its release is cut and freed. It is the backstop for a release that
stays audible; one that falls below the chip's silence is freed then.

## 7. Pitch, vibrato and portamento

Pitch is kept in 1/4096 semitone (`49152` an octave), as `log2(fnum × 2^block)`. A4 (note 69) is
440 Hz, and the chip runs at 14318180 / 288 Hz. A voice's pitch is the sum of: key × 4096 (the note, or
for a drum or a fixed-note patch the patch's key); the patch's note offset for that voice; the
pseudo-4-op second voice's detune; bend × range; RPN fine and coarse tuning; master fine and coarse
tuning; vibrato; and the portamento glide.

**F-number and block.** The block is the one that puts the F-number in 512-1023, the largest that fits
and so the finest step. The F-number is `2^fraction × 512` rounded to the nearest, from a 769-entry table
with linear interpolation. Below block 0's range the F-number drops under 512 at block 0. Above block
7's it stays at block 7, F-number 1023. The result is within a cent of the target wherever the chip's
step allows it: the step is under 2 cents from F-number 866 up. Elsewhere it is the nearest step. The
tests check every note 0-127, and bend extremes at ranges 2, 12 and 24.

**Detune** (pseudo-4-op second voice): WOPL's byte X gives `((X + 128) >> 1) - 64` thirty-seconds of a
semitone (about 3.1 cents each), as the WOPL specification gives it.

**Vibrato (CC 1)** is the driver's own, separate from the chip's LFO vibrato that patches use through
their own bits. It is a sine (a 256-step table) at 5.5 Hz. Its depth is ±50 cents at CC 1 = 127 and
proportional below that. It moves the F-number at the control period. Its phase starts at 0 when the
depth rises from 0, and runs on while the depth is above 0. These values are a starting point: they
have not yet been tuned by ear.

**Portamento.** With CC 65 on and CC 5 above 0, a Note On glides from the channel's last note to its
own pitch. The curve is linear in pitch (equal cents per period). The time is `(t² × 3 + 4) / 8`
control periods for CC 5 = t, about t²/2 ms: 0.5 ms at 1, 50 ms at 10, 0.8 s at 40, 2 s at 64 and 8 s at
127. It is independent of the interval. CC 84 (portamento control) makes the next Note On glide from
that key with CC 5's time, whether CC 65 is on or not. It applies once.

## 8. Levels, pan and sends

**Curves.** Velocity (after the patch's velocity offset, clamped to 1-127), CC 7, CC 11 and master
volume become one attenuation in the chip's 0.75 dB steps:

- **hirav** (the default): General MIDI's curve (GM2 3.3.1). Each value attenuates by
  `40·log10(127 / x)` dB, and the four are summed and rounded once to the nearest step. Any value of 0 is
  silent. The table is Q32 in 64 bits, generated offline. Q20 rounded 60 of the 127⁴ sums the wrong way
  at the half-step; Q32 gives the formula's rounding for every one, which the tests check exhaustively.
- **linear** (`CURVE_LINEAR`, the driver's own straight line; not the generic model, `CURVE_GENERIC`): the four values' product `p = v·c7·c11·m / 127⁴`, mapped linearly onto total-level
  steps: `round(63 × (1 - p))`, worked in integers (each product rounded to 127² scale). At full
  scale it adds nothing; at 0 it adds 63 steps. It is linear in the chip's steps, so its dB curve is
  the cards' simple one.
- **table**: the caller's `vel[128]` and `vol[128]` (the second serves volume, expression and master),
  in 1/16 steps, summed and rounded once. `0xFFFF` is silent.
- **the sound drivers' models** (`CURVE_DMX` .. `CURVE_OCONNELL`, and `CURVE_GENERIC`, `CURVE_NATIVE`): below.

**The sound drivers' volume models.** DMX (`CURVE_DMX`, `CURVE_DMX_FIXED`), the Apogee Sound System
(`CURVE_APOGEE`, `CURVE_APOGEE_FIXED`), the Windows 9x SB16 and generic FM drivers (`CURVE_9X`,
`CURVE_9X_GENERIC_FM`), the Audio Interface Library (`CURVE_AIL`), HMI SOS 4 and 3 (`CURVE_HMI`,
`CURVE_HMI_OLD`), the MS AdLib driver for Windows 9x (`CURVE_MS_ADLIB`), IMF Creator (`CURVE_IMF_CREATOR`)
and Jamie O'Connell's FM synth (`CURVE_OCONNELL`), and the generic and native models (`CURVE_GENERIC`,
`CURVE_NATIVE`; drv 0.5.0): the ways those drivers turned velocity and volume into
the chip's levels, which banks made for them (WOPL's volume model) and programs ported from them expect.

**Their source: black-box measurement, every one.** No driver's source and no documentation of their
arithmetic were used. The numbers come from libADLMIDI, which carries these models, measured as a black box:
notes rendered through its public interface with an additive 2-op probe patch (the operators at x1 and x2,
each read from its own partial with a flat-top window) showed each operator's level in the chip's steps.
Patch levels 0 to 63 against every velocity, every channel volume, and two or more inputs at once. The
measuring harness and the fitting script are not part of this repository; `drv/hvopl3_drv_models.inc`
and the tests' `models_measured.inc` and `models_combined.inc` are their output. So each model here is
what libADLMIDI does, as far as it could be seen, and not checked against the original drivers. No
libADLMIDI source was read.

**Their arithmetic** (`model_tl`; the tables in `drv/hvopl3_drv_models.inc`): the velocity v (after the
patch's offset) and the channel volume c = (CC 7 x CC 11 / 127) x master / 127 -- a product index, which
every model takes exactly so -- each have a 128-entry table, and the operator's level comes from the
patch's own level tl by the model's family:

| Family | Level | Models |
|---|---|---|
| scale toward 63 | 63 - R((63 - tl) k / div), its divisor and rounding its own | DMX, IMF, generic, native (div 63, rounded up), AIL (127, down), MS AdLib (127, nearest), Apogee (1024, down), O'Connell (64, down) |
| add | tl + a | the two 9x |
| scale with an offset | 63 - ((63 - tl) K + B) / 64 | the two HMI |

Velocity and volume combine by the model's own rule: their attenuations as fractions of 63 multiplied
(DMX, IMF), their factors multiplied over the full-volume factor (Apogee, AIL, O'Connell), attenuations
added (9x; generic, which then scales by the sum), or one table at the index v c / 127 (HMI, MS AdLib,
native; velocity alone takes its own table).
Every model reproduces the measurements exactly for one input at a time, at every patch level (the tests
check 336 such points). With two or more inputs at once the measured arithmetic could not be pinned down
exactly; against 700 measured combinations (two-input grids, random four-input points) the models give:

| Model | exact | mean error | worst |
|---|---|---|---|
| DMX, DMX_FIXED, IMF_CREATOR | 600/700 | 0.14 steps | 2 |
| APOGEE, APOGEE_FIXED | 626/700 | 0.11 | 1 |
| 9X | 693/700 | 0.03 | 5 |
| 9X_GENERIC_FM | 691/700 | 0.03 | 5 |
| AIL | 584/700 | 0.17 | 1 |
| HMI, HMI_OLD | 489/700, 473/700 | 0.83 | 5 |
| MS_ADLIB | 696/700 | 0.05 | 32 (4 points near silence) |
| OCONNELL | 342/700 | 1.28 | 15 |
| GENERIC | 513/700 | 0.39 | 9 |
| NATIVE | 663/700 | 0.05 | 1 |

A step is 0.75 dB. O'Connell's combination is the least known: velocity and volume there act like a sum
of finer attenuations than its tables hold.

**Which operators.** The heard operators, as for the other curves; in FM the modulator keeps the bank's
level under every model (measured). Two models treat a 2-op voice's first operator apart, when it is heard
(additive): Apogee gives it its own attenuations, added (`CURVE_APOGEE_FIXED` treats it as the second); HMI
3 never scales it. DMX and DMX_FIXED measured the same; whatever "fixed AM voices" changed did not show in
2-op voices. A 4-op voice's heard operators all take the second operator's rule. HMI 3 in FM mode measured
differently from HMI 4 (its modulator apparently silenced, its carrier a few steps off) and is not
reproduced there: drv plays it as HMI 4's carrier.

**Level corrections only with hirav.** The models replace the hirav curve's added dB with their own
scaling, so a patch's gain correction (measured under hirav) would not mean the same: with any model the
corrections are left out (gain 0), as with linear and table.

The attenuation is added to the total level of the operators the voice's sound comes out of: the
carrier of an FM 2-op voice, both operators of an additive one, and for 4-op the carriers of its
connection (FM-FM: 4; AM-FM: 1 and 4; FM-AM: 2 and 4; AM-AM: 1, 3 and 4). The other operators keep
the bank's levels, so timbre holds as the volume changes. Each operator saturates at 63.

**Gain remainder** (`gain_remainder`, off by default): when the loudest carrier would pass 63, the
excess goes to `set_gain` instead (-32 at most), so very quiet notes keep falling.

**Level corrections** (`level_corrections`, on by default): a patch's `gain` field (0.75 dB steps,
±16) is applied as the voice's `set_gain`. That is a gain after the chip makes the voice, so the
patch's timbre and its whole range of dynamics are untouched. It applies with the hirav curve only.
The driver carries no correction data. The caller passes tables to `set_levels`: one for every
melodic bank's programs, and per-key tables for kits by LSB (a kit with no table takes kit 0's).
Hira-V passes its measured `gm_levels.inc`, so a recalibration needs no driver change.
`set_levels` writes the patches in the pool, so it must run again after more banks are loaded.

**Pan (CC 10).** Soft pan by default: `set_pan` on the voice's channel (0-127, the chip's
constant-power law). With `hard_pan`, the chip's C0 left/right bits, as the cards had it: 0-42 left,
43-85 both, 86-127 right. Those are thirds of the range, with the centre (64) in the middle third. The
chips then run with `NO_PAN_LAW`, so one side is at unity, not the -3 dB of a centred soft pan.

**Sends (CC 91, 93)** through `set_sends` on every voice of the channel. **Deep tremolo and vibrato**
(register BD) come from the bank's flags (the last WOPL loaded), or are forced by `deep_tremolo` and
`deep_vibrato`. Rhythm mode is never used: BD's percussion bits stay clear, and patches flagged for it
play as ordinary voices.

## 9. Banks and the WOPL loader

A bank is (melodic or percussion, MSB, LSB) × 128 patches. Banks live in the caller's pool, found by a
hash (open addressing, at most half full), so lookup costs the same whatever the number of banks.
`set_patch` makes a bank when needed and fails cleanly when the pool is full. Banks never move, and a
new bank's patches start blank.

`load_wopl` reads OPL3 Bank Editor's WOPL format, versions 1 to 3, as its published specification
describes. Every read is bounds-checked against `size`. It returns `LOAD_FORMAT` (not WOPL, or an
MSB/LSB past 127), `LOAD_VERSION`, `LOAD_TRUNCATED` or `LOAD_FULL` (the pool lacks room for the file's
new banks), and changes nothing unless the whole file loads. The tests check DMXOPL3 field by field
against the file, every truncation over the header and metadata, random truncations, malformed headers
and a fuzz of damaged files under the address and undefined-behaviour sanitizers.

- **Operators:** WOPL lists carrier 1, modulator 1, carrier 2, modulator 2; the patch stores them in
  the chip's order (modulator first).
- **Kinds:** flag 0x04 is blank. Otherwise 0x02 is pseudo-4-op (DMXOPL3 sets 0x01 with it, so 0x02 is
  decisive), 0x01 alone is 4-op, and neither is 2-op. A patch whose registers and connections are all
  zero is blank too, since it could never sound, so it falls back like a missing one.
- **Fields:** the note offsets (big-endian, signed), velocity offset, detune, percussion key, the
  rhythm-mode drum type (bits 3-5, kept) and the fixed-note flag (0x40: a melodic patch that plays at
  its percussion key). Version 3's two delays are not used.
- **Bank numbers:** versions 2 and 3 carry each bank's MSB and LSB. Version 1 has none: melodic bank i
  is MSB i, LSB 0, and percussion bank i is MSB 0, LSB i (so kit i is program i).
- **Bank-wide:** the deep tremolo and vibrato flags, and the volume model, as the WOPL specification
  numbers it: 2 DMX, 3 Apogee, 4 Windows 9x, 5 DMX fixed, 6 Apogee fixed, 7 AIL, 8 Windows 9x generic FM,
  9 HMI 4, 10 HMI 3, 11 MS AdLib, 12 IMF Creator, 13 O'Connell -- each the driver's model of that name;
  1 (the chip's native logarithmic scale) becomes hirav, as both add attenuation in the chip's log domain;
  0 becomes the driver's default, hirav. The specification calls 0 "generic, linearized", but banks that
  name no model store 0 (DMXOPL3 does), so 0 is taken as "the driver's choice". Past 13, the default.
  (Before drv 0.3.0 the loader read the numbers one off: 1 as generic and 2 as native.) So a bank never
  selects the generic or native model (`CURVE_GENERIC`, `CURVE_NATIVE`): only an explicit choice does
  (`Config::curve`, or a host's own mapping).

## 10. The command stream

With `Config::stream`, the driver drives no chips. `render_stream` writes the block's HVO2 records
([TRACE-FORMAT.md](TRACE-FORMAT.md)) into the caller's buffer: register writes, pan, sends, gain,
resets and runs. Whatever owns the chips replays them with `hvopl3::play(chips, n, records, count,
out, rate, chip_flags(drv))`. The tests check that the replay gives direct mode's samples exactly:
dry and both buses, on 1 to 32 chips, at 48 and 96 kHz, in high quality, with hard pan, and with
blocks split by a small buffer.

- The chips get `RESET` records at the first block. The other set-up writes follow as `REG` records.
- HVO2 gives the chip 5 bits (5..4 and 31..29), so 32 chips; HVO2 is the only layout `play` reads. At 96 kHz the runs set bit 22 (frames at the replay's rate).
- The driver keeps the `Chip`s given to `init` as **shadows**. It sends them every write and advances
  them with `hvopl3::advance`: keys and envelopes without synthesis. Their `active` bits drive its
  decisions exactly as the real chips' do, at a small fraction of a render's cost.
- **Buffer size.** `capacity` must be at least `stream_reserve()` (20 records a slot plus a little: 6.2K
  records for 16 chips, 11.6K for 32). Before each message and each control period, the driver checks that the
  worst case fits. If not, it ends the call there and returns the frames done, and the unapplied
  messages stay queued. The caller sends the records, then calls again for the rest of the block. A
  buffer under the reserve gets no progress at all.

## 11. Speed

**The A25** (Hira-V's emulator, which counts instructions; the Tang's flags), with DMXOPL3:

| Song | Chips | Driver alone | The chips' render | Driver / chips |
|---|---|---|---|---|
| The test song (`tests/song.hpp`, 8 s) | 1 | 56 | 1,053 | 5.3% |
| The test song | 4 | 66 | 3,826 | 1.7% |
| Song A: a piano ballad, 274 messages | 1 / 4 | 32 / 36 | 713 / 990 | 4.5% / 3.7% |
| Song B: a band arrangement, 667 messages | 1 / 4 | 39 / 45 | 980 / 2,549 | 3.9% / 1.7% |
| Song C: an SC-88 demo, 1,926 messages | 1 / 4 | 47 / 50 | 1,086 / 2,913 | 4.3% / 1.7% |
| Song D: an SC-88 demo, 5,672 messages | 1 / 4 | 60 / 68 | 1,301 / 3,872 | 4.6% / 1.7% |

The figures are instructions per 48 kHz frame. "Driver alone" is everything in `render` except the
chips' `hvopl3::render` calls (`bench/a25/drv.sh` counts them apart with `HVOPL3_DRV_CHIP_RENDER`).
Songs A-D are real General MIDI files, not in the repository: 8 s of each from 60 s in
(`mid2wav --dump F --dump-from 60`, then `EVENTS=F sh bench/a25/drv.sh`).

The target was at most 25% of the chips' cost for a busy General MIDI song. Per message the work is
bounded: a hash lookup, the channel's own voices, and at most 32 entries of a voice list. Resets, All
Sound Off and master volume touch every voice. Only channels whose state changed (bend, vibrato, a
glide) are touched at the control period.

On the host (`bench/build/mid2wav`), songs render at 0.6-1% of one core with two chips.

## 12. Tests

```sh
make -C tests              # t_ext (the chip), t_drv (the driver), t_drv_asan (under sanitizers), t_drv4 (HVOPL3_DRV_MAX_CHIPS=4)
sh tests/plant_drv.sh      # 51 planted errors in the driver; every one must be caught
sh bench/vec/drv.sh        # the test song's digests on x280, v128, t2, baby, rv64 under qemu; c920 built
sh bench/a25/drv.sh        # the same on the A25 under rv32emu, and its instruction counts
make -C bench && bench/build/mid2wav SONG.mid OUT.wav [--levels gm_levels.inc] [--chips N] ...
```

`t_drv` checks each message's effect on the chip's registers and extension state. It covers:

- the pedals, re-strike, the RPNs, Reset All Controllers, master volume and tuning, the resets;
- every percussion route on and off, two drum channels at once, the reset rules;
- every note's pitch, bend extremes, vibrato and portamento;
- each curve (hirav exhaustively), the remainder and the corrections;
- the WOPL loader;
- 4-op connections, pseudo-4-op, kits and fallbacks;
- the balance over chips and the steal policy;
- no leaks: a seeded random stream on 1, 2, 4, 9, 16 and 32 chips, then every channel free;
- block sizes, and the stream against direct mode;
- `update`: each live setting changed with a note sounding, and the changes that must reset;
- the returning note: 2-op, 4-op and pseudo-4-op voices keyed again from their level, and the cases that are not;
- a released voice freed when the chip says it is inaudible, and cut then;
- every volume model at 336 measured single-input points exactly, and at 226 combined points where it agrees with the measurements;
- GS's per-drum settings: each, on a sounding note, map 2 apart, the reset rules.

`bench/build/mid2wav` renders a Standard MIDI File given on its command line to a WAV, for listening.
Never commit MIDI files or WAVs.
